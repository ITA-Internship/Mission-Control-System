# Mission Control Frontend

React and TypeScript frontend for the Mission Control System.

## Requirements

Before starting the frontend, make sure the following tools are installed:

- Node.js 24+
- npm

Check the installed versions:

```bash
node --version
npm --version
```

The frontend test stack now depends on `jsdom@30`, which requires Node 24+.
The GitHub Actions workflow already runs frontend checks on Node 24.

## Install dependencies

Open the frontend directory:

```bash
cd frontend
```

Install dependencies:

```bash
npm install
```

Create the local frontend environment file.

### PowerShell

```powershell
Copy-Item .env.example .env.local
```

### Git Bash

```bash
cp .env.example .env.local
```

The local frontend environment file should contain:

```dotenv
VITE_API_BASE_URL=
API_PROXY_TARGET=http://127.0.0.1:8000
VITE_CSRF_COOKIE_NAME=csrftoken
VITE_CSRF_HEADER_NAME=X-CSRFToken
```

Do not commit `.env.local`.

## Local development modes

The project supports two local development modes.

## 1. Vite development mode

Use this mode while developing frontend pages.

Start the Django backend on:

```text
http://127.0.0.1:8000
```

In the root backend `.env` file, set:

```dotenv
DEBUG=True
FRONTEND_URL=http://127.0.0.1:5173
CSRF_TRUSTED_ORIGINS=http://localhost:8000,http://127.0.0.1:8000,http://localhost:5173,http://127.0.0.1:5173
ALLOWED_HOSTS=localhost,127.0.0.1
```

In `frontend/.env.local`, use:

```dotenv
VITE_API_BASE_URL=
API_PROXY_TARGET=http://127.0.0.1:8000
VITE_CSRF_COOKIE_NAME=csrftoken
VITE_CSRF_HEADER_NAME=X-CSRFToken
```

Start the frontend:

```bash
npm run dev -- --host 127.0.0.1
```

The frontend will be available at:

```text
http://127.0.0.1:5173
```

Frontend API requests use relative `/api` URLs.

For example, the browser sends a request to:

```text
http://127.0.0.1:5173/api/accounts/users/password-reset/
```

The Vite development server proxies it to:

```text
http://127.0.0.1:8000/api/accounts/users/password-reset/
```

Password-reset and account-activation email links generated by the backend will use:

```text
http://127.0.0.1:5173
```

---

## 2. Docker Compose mode

Use this mode to test the production-like Nginx and frontend build.

In the root backend `.env` file, set:

```dotenv
DEBUG=True
FRONTEND_URL=http://127.0.0.1:8000
CSRF_TRUSTED_ORIGINS=http://localhost:8000,http://127.0.0.1:8000
ALLOWED_HOSTS=localhost,127.0.0.1
```

Build and start the application:

```bash
docker compose up -d --build
```

The frontend and backend will be available through Nginx at:

```text
http://127.0.0.1:8000
```

The frontend routes are served by the React single-page application, while `/api/` requests are proxied to Django.

Password-reset and account-activation email links generated by the backend will use:

```text
http://127.0.0.1:8000
```

Do not run the Vite development server when testing this mode.

## Supported backend connection model

The supported configurations are:

- relative `/api` requests through the Vite development proxy;
- same-origin `/api` requests through the production Nginx container.

Separate-origin frontend and backend deployment requires additional backend CORS configuration and is not enabled by default.

Setting `CSRF_TRUSTED_ORIGINS` does not configure CORS.

## Frontend environment variables

### `VITE_API_BASE_URL`

Base URL used by frontend API requests.

For the supported local setup, leave it empty:

```dotenv
VITE_API_BASE_URL=
```

This makes the frontend use relative `/api` requests.

### `API_PROXY_TARGET`

Backend URL used by the Vite development proxy:

```dotenv
API_PROXY_TARGET=http://127.0.0.1:8000
```

This variable is used only by the Vite development server.

### `VITE_CSRF_COOKIE_NAME`

Django CSRF cookie name:

```dotenv
VITE_CSRF_COOKIE_NAME=csrftoken
```

### `VITE_CSRF_HEADER_NAME`

Header used to send the CSRF token:

```dotenv
VITE_CSRF_HEADER_NAME=X-CSRFToken
```

Session-based API requests use:

```text
credentials: include
```

Unsafe requests include the Django CSRF token when the CSRF cookie is available.

For session sign-in, the frontend first performs a safe `GET /api/accounts/login/`
request to bootstrap the Django CSRF cookie, then sends the login `POST` with
the configured `X-CSRFToken` header.

## Authentication routes

The frontend provides the following routes:

```text
/login
/forgot-password
/reset-password/:uid/:token
/activate/:userId/:token
/change-password/required
```

Example development URLs:

```text
http://127.0.0.1:5173/login
http://127.0.0.1:5173/forgot-password
http://127.0.0.1:5173/reset-password/demo-uid/demo-token
http://127.0.0.1:5173/activate/1/demo-token
http://127.0.0.1:5173/change-password/required
```

```text
http://127.0.0.1:8000/login
http://127.0.0.1:8000/forgot-password

http://127.0.0.1:8000/activate/1/demo-token
```

## Administration console

The administration console renders inside the shared application shell
(`src/shared/layout/AppShell.tsx`), behind the session guard in
`src/app/ProtectedRoute.tsx`:

```text
/administration?tab=users
/administration?tab=units
/administration?tab=audit
```

The active tab is stored in the `tab` query parameter, so a tab is
linkable and survives a reload.

### Access

The console is for the **Admin** role only. The sidebar hides the entry
for every other role (`allowedRoles` in `src/shared/layout/navigation.ts`),
and the route redirects a non-admin to `/dashboard`, so a deep link
neither renders the console nor fires an administration request. This
mirrors `accounts/rbac.py`, where no other role holds the `users.*` or
`audit_logs.view_all` permissions the console depends on.

### Backend endpoints used

| Console area | Endpoint | Available in the API |
|--------------|----------|----------------------|
| Audit log table | `GET /api/accounts/audit-log/` | yes |
| Audit log CSV export | `GET /api/accounts/audit-log/export/` | yes |
| Create user | `POST /api/accounts/users/` | yes |
| Activate / deactivate user | `PATCH /api/accounts/users/<pk>/status/` | yes |
| Change user role | `PATCH /api/accounts/users/<user_id>/role/` | yes |
| Users table | `GET /api/accounts/users/` | not yet |
| Military units table and forms | `/api/accounts/military-units/` | not yet |
| Role selects and filters | `GET /api/roles/` | not yet |

The three endpoints marked "not yet" are part of the administration
contract in `docs/design/administration.md` but are not exposed by the
backend. Until they exist, the affected tables render an explicit
"endpoint unavailable" state, and role or unit selects are disabled
instead of showing empty data.
